# DirectInput Hardware Scancode Subsystem Architecture

**Version:** 2.0 Native C  
**Date:** 2026-09-21  

---

## 1. Hardware vs Virtual Key Dispatch

Windows input processing is divided into three distinct layers:
1. **Raw Driver / Hardware Scancodes (Set 1 / Set 2 PS/2 & HID):** Sent directly by hardware keyboard controllers. DirectInput / Raw Input reads at this layer.
2. **Virtual Keys (`VK_...`):** Translated by `user32.dll` keyboard layout tables.
3. **Window Messages (`WM_CHAR`, `WM_KEYDOWN`):** Generated by `TranslateMessage` and posted to window message queues.

```
+-------------------------------------------------------------------------+
|                  WINDOWS INPUT PROCESSING PIPELINE                      |
+-------------------------------------------------------------------------+
|                                                                         |
|  [ Physical Keyboard / HID Device ]                                     |
|           | (Hardware Scancodes)                                        |
|           v                                                             |
|  [ Kernel Input Driver / Raw Input Ring Buffer ] <-----+ (DirectInput)  |
|           |                                            |                |
|           v                                            |                |
|  [ WH_KEYBOARD_LL Hook ] <----+ (Tobelsoft Hook)       |                |
|           |                   |                        |                |
|           v                   | (O(1) Evaluation)      |                |
|  [ Windows Virtual Key Engine |                        |                |
|           |                   v                        |                |
|           v          [ SendInput(KEYEVENTF_SCANCODE) ]-+                |
|  [ Application Message Queue (WM_KEYDOWN) ]                             |
+-------------------------------------------------------------------------+
```

## 3. Anti-Looping & Injected Event Filtering

When `SendInput` injects a synthetic keystroke, Windows passes that keystroke through `WH_KEYBOARD_LL`. If unchecked, the macro engine would detect its own injected key as a trigger, creating a catastrophic recursive infinite loop.

Tobelsoft Macro enforces zero-overhead protection by checking the `LLKHF_INJECTED` bit:
```c
if (kbd->flags & LLKHF_INJECTED) {
    // Keystroke was synthesized by SendInput - bypass trigger check immediately
    return CallNextHookEx(NULL, nCode, wParam, lParam);
}
```

## 4. Input Suppression Mechanics

When a macro has `suppress_original_input = true`:
- The hook procedure consumes the physical keystroke by returning non-zero (`return 1`).
- The physical keystroke is completely withheld from the foreground application.
- The macro worker thread then synthesizes the configured action sequence instead.
- If `left_click_safety_lock` is active on mouse triggers, suppression is automatically bypassed to protect user system control.
